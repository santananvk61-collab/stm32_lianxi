# 项目问题排查记录

> 项目：GNB_project —— 基于 STM32F103C8T6 的温湿度气压监测仪
> 硬件：SSD1306 OLED（128×64）+ AHT20（温湿度）+ BMP280（气压/温度）
> 记录：开发过程中踩过的坑、定位思路和最终解决方案

---

## 一、OLED 显示类

### 1. 中英混排时英文比汉字小一号

**现象**：屏幕上 `波特律动V2.0` 这类混排文字，英文 V2.0 又小又矮，和 16×16 的汉字不成比例。

**根因**：当时英文走的是 5×7 点阵字库（宽 6 高 8），汉字走 16×16 字库，两者高度差一倍。

**解决**：引入"半角字库"概念——英文用 8×16 字库（宽 8 高 16），和 16×16 汉字**同高、宽度正好 1:2**，这才是 PC 上中文软件的标准排版规则。5×7 小字库保留给纯英文紧凑显示。

**教训**：中英混排时，英文字库的高度必须和汉字一致，宽度必须是汉字的一半，否则必然一大一小。

---

### 2. 汉字上下两行糊成一片

**现象**：16×16 汉字按 16 像素行距排，上下两行的墨迹贴在一起。

**定位**：写脚本量了每个字模的"墨迹行范围"，发现 16×16 汉字（波/特/律/动/度/气）墨迹**占满第 0~15 行，上下零留白**。行距 16 时，上一行最后一个墨点在 y=31，下一行第一个墨点在 y=32，**空隙 = 0**。

**根因**：把"行距"和"字号"当成一回事了。`48÷3=16` 算出来的是行距，不是能直接当字号用。

**解决**：改用 **12×12 字 + 行距 16**。12×12 汉字墨迹在第 1~11 行（自带留白），行距 16 时实际空隙 5 像素。

**教训（通用公式）**：**行距 = 字号 + 2~4px。先定行距，再选 ≤ 行距-2 的字号。**

---

### 3. 8×8 汉字糊成一团

**现象**：把汉字也压到 8×8，结果"温、湿、波、律、特"这些字糊成实心块，认不出来。

**根因**：8×8 只有 **64 个像素点**，而"温"字有 12 笔以上，物理上放不下。笔画少的字（气、压、度）勉强能认，笔画多的必糊。

**解决**：放弃 8×8 汉字，最小用 12×12（宋体在 12px 有内嵌点阵，是"能看清"的最小尺寸）。

**教训**：点阵字体的笔画数受限于像素总数。8×8=64 点，只能放 4 笔左右的简单字；12×12=144 点才够常见汉字。

---

### 4. 每个中文字少了一像素行（字模被裁掉底部横线）

**现象**：程序能跑，但每个汉字的底部横线都缺了（"温/湿"的皿底、"气"的乛底）。

**定位**：先排除代码——`DrawGlyph` 逐行绘制逻辑正确，字库数据里"温"第 11 行也确实有墨点。然后用 Python 把宋体 12px 的字**画进一个 18 行高的框**，发现墨迹实际占**第 1~12 行**（比 12 高多出 1 行）。

**根因**：生成字库时只取了 0~11 行，**第 12 行（底部横线）被整个裁掉了**。不是"不支持 12×12"，是生成时的裁剪 bug。

**解决**：生成字模时把字往上移 1 像素——`draw.text((0, -1), ch, ...)`，墨迹就变成 0~11 行完整装下。

**教训**：用 PIL 渲染字模后，**一定要校验墨迹行范围是否正好落在框内**，不能想当然认为"字号 N 就占 N 行"。ASCII 小写 g/y/p/q/j 的下伸部同样会超框。

---

### 5. `// \` 行尾反斜杠吃掉了下一个字模

**现象**：字库表比预期少了一个条目（95 个变成 94 个），`]` 之后所有字符错位。

**定位**：用 `arm-none-eabi-nm --print-size` 看符号大小，发现 `FontASCII8x8` 是 752 字节 = 94 条（应为 95×8=760）。

**根因**：字模那行的注释写成了 `// \`。**C 语言里行尾的反斜杠是"续行符"**，会把下一行也并进注释，于是下一行字模数据被注释掉了。

**解决**：注释标签改成 `// backslash 反斜杠`。

**教训**：生成字模注释时，标签里**不要以反斜杠结尾，也不要出现花括号**（花括号会干扰正则解析脚本）。

---

## 二、BMP280 传感器类

### 6. 读取卡死在 while 死循环

**现象**：调用 `BMP280_Get()` 卡死，注释掉才正常。

**定位**：旧代码是这样的：

```c
uint8_t status;                      // ① 局部变量，没赋初值
do {
    BMP280_ReadRegs(0xF3, &status, 1);  // ② 不检查返回值
} while (status & 0x08);             // ③ 拿 bit3 判断
```

**根因**：三个问题凑一起就必然卡死——
- `status` 是局部变量，初值是栈上的垃圾值；
- `HAL_I2C_Mem_Read` 失败时（总线 BUSY）立即返回，`status` 根本没被写入；
- STM32F1 的 I2C 特别容易卡在 BUSY 状态，一旦卡住每次读都失败，`status` 永远是垃圾值。如果垃圾值 bit3=1，死循环。

**解决**：重写驱动为**全阻塞 + 带超时**：
- 所有读写带 100ms 超时（出问题会返回失败，绝不死等）；
- 每一步检查 HAL 返回值；
- 读数据前**轮询状态位(0xF3 bit3)**确认转换完成，用 `HAL_GetTick()` 做超时。

**教训**：`HAL_MAX_DELAY` = 死等；`while(1)` 不加超时 = 死循环。嵌入式里凡是"等"的地方都要有超时。

---

### 7. 读取用中断、写入用阻塞，不对称

**现象/疑问**：为什么只有读取是中断的，写入不是？

**定位**：算了一笔账——写 1 字节命令约 0.2ms，读 6 字节约 0.7ms，而**芯片转换要 41ms 才是大头**。既然 41ms 都在等，读那 0.7ms 用不用中断根本没区别。

**解决**：改成**全阻塞**。中断省不下时间，反而要多写两个回调 + 一层状态机，更容易出错。

**教训**：非阻塞的收益只在于"能并行干别的事"。当等待本身就是瓶颈时，非阻塞是纯增加复杂度。

---

### 8. 气压数值算出来不对（Q24.8 单位坑）

**现象**：怀疑整数气压补偿公式有 bug，算出来的数离谱。

**定位**：用 Python 精确模拟 C 的 int64_t 运算（含溢出回绕），和浮点版公式交叉验证。发现整数版结果是 25767233，浮点版是 1006.53，**正好差 256 倍**。

**根因**：数据手册写得很隐蔽——整数气压补偿返回的是 **Q24.8 格式，即真实帕斯卡数 × 256**（手册原话："24674867 代表 24674867/256 = 96386 Pa"）。公式本身没问题，是**单位理解错了**。

**解决**：要 Pa 就 `/256`，要 hPa（百帕）就 `/25600`。

**教训**：拿到补偿公式先别急着怀疑公式，先查返回值的**单位/定点格式**。Q24.8、Q0.8 这类"定点数"格式是传感器手册的常见坑。

---

### 9. 气压显示为 0，但温度"正常"

**现象**：屏幕上气压一直是 0.0，温度却显示正常。

**定位**：关键发现藏在 main.c 的调用顺序里：

```c
BMP280_Analysis(&pressure, &temperature);   // BMP280 写了一遍 temperature
AHT20_Analysis(&humidity, &temperature);    // AHT20 又写了一遍，覆盖！
```

**根因**：
- `temperature` 被写了两遍，第二遍（AHT20）覆盖了第一遍（BMP280），所以"温度正常"其实是 AHT20 的温度，跟 BMP280 无关；
- `pressure` 只有 BMP280 写，BMP280 初始化/读取失败时 `Analysis` 直接返回 0 不改 `pressure`，它就一直停在 0.0。

**解决**：先查 `BMP280_Read_ID()`——返回 0x58 是 BMP280 正常，0x60 是 BME280（地址不同），0x00 是没接上/地址错（0x76 和 0x77 要试）。

**教训**：多个传感器输出到同一个变量时，要警惕"后面覆盖前面"。**"某个值正常"不能证明对应的传感器在工作**。

## 三、通用 C 语言坑

### 10. sizeof 跨文件不能用于 extern 数组

**现象**：想在头文件里用 `sizeof(FontCN16x16)/sizeof(...)` 自动统计字库条目数，编译报错。

**根因**：头文件里声明的 `extern` 数组是"不完整类型"（第一维没写死），`sizeof` 无法作用于不完整类型。

**解决**：在 font.c 里（能看见数组完整长度的编译单元）用 `sizeof` 统计好，导出成变量 `CN_FontCount`。校验时可用 `arm-none-eabi-nm --print-size` 看符号字节数 ÷ 每行字节数。

**教训**：`sizeof` 只能在"能看到数组完整定义"的地方用。

---

### 11. WriteInt 的缓冲区太小，会栈溢出

**现象/隐患**：`SSD1306_WriteInt` 里 `char buf[6]` 只能存 5 位数字 + 结尾 \0，`int` 最多 10 位，超过就**越界写栈**。

**解决**：
- `char buf[12]`（32 位整数最多 10 位 + 负号 + \0）；
- 用 `do-while` 处理 `val == 0` 的情况；
- 用 `-(val+1)+1` 绕开 `INT_MIN` 取反溢出的坑。

**教训**：字符串缓冲区大小要按"最坏情况位数"来算，不能拍脑袋。

---

## 四、排查方法论总结

1. **用数据说话**：实测字节数、墨迹行范围、像素间隙，比"我觉得"有说服力。
2. **先缩小范围**：数据层（字库字节）→ 代码层（绘制逻辑）→ 硬件层（屏/传感器），一层层排除。
3. **交叉验证**：同一个公式用两种实现（浮点版 vs 整数版）对算，结果不一致就说明有一处错了。
4. **可视化**：把字库数据逐像素渲染成图片，一眼就能看出"少了一行"、"糊成一团"这类问题。
5. **超时是铁律**：嵌入式里凡是"等"，都要有超时；凡是"读/写"，都要检查返回值。

```
Core/
  Inc/  font.h      字库头（字号/行距常量）
        oled.h      OLED 总入口头
        oled_text.h 文字模块头
        bmp280.h    BMP280 驱动头
        aht20.h     AHT20 驱动头
  Src/  font.c      字模数据（纯数据）
        oled.c      核心：显存 + 图元
        oled_text.c 文字排版
        bmp280.c    气压/温度驱动
        aht20.c     温湿度驱动
        main.c      主程序
```

三个模块单向依赖：`oled_text` → `oled`(DrawPixel) → `font`(字模数据)。
